# Codex — Database Tables Reference

---

## PostgreSQL: 8 Tables

---

### 1. `documents` — Policy Document Registry
**Purpose:** Stores metadata for each ingested policy document.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated via `gen_random_uuid()` |
| `title` | TEXT | Document name, e.g. "Password Management Policy" |
| `type` | VARCHAR(50) | Category: "security", "compliance", etc. |
| `owner` | VARCHAR(100) | Responsible department or person |
| `version` | VARCHAR(20) | "v1", "v2.1", etc. |
| `effective_date` | DATE | When the policy takes effect |
| `status` | VARCHAR(20) | "active", "archived", "draft" — defaults to "active" |
| `source_uri` | TEXT | Original file path, e.g. `archive/...docx` |
| `access_tags` | JSONB | Access control list, e.g. `["public", "internal"]` |
| `created_at` | TIMESTAMP | When the record was inserted |
| `updated_at` | TIMESTAMP | Last update timestamp |

**Relationships:** Has many `chunks` (cascade delete), has many `entities`

---

### 2. `chunks` — Clause-Level Text Units
**Purpose:** Stores the actual searchable text of each clause, plus its vector embedding.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `document_id` | UUID (FK) | References `documents(id)` — **cascade delete** (delete doc = delete chunks) |
| `section_path` | TEXT | Hierarchical location, e.g. `"4.2.1 > Password Policy"` |
| `clause_ref` | VARCHAR(100) | Clause number, e.g. `"4.2.1"` or `"Rule 3"` |
| `page` | INTEGER | Page number in original document |
| `text` | TEXT | The actual clause content (non-nullable) |
| `embedding` | vector(1024) | 1024-dim float vector from bge-large-en-v1.5 |
| `token_count` | INTEGER | Number of tokens in this clause |
| `version` | VARCHAR(20) | Document version this chunk belongs to (denormalized from documents) |
| `created_at` | TIMESTAMP | Insertion time |

**Relationships:** Belongs to one `document`, has many `citations`

**Indexes:** `document_id`, `clause_ref`, plus optional IVFFlat vector index

---

### 3. `entities` — Extracted Rules & Thresholds
**Purpose:** Structured extractions from policy text — deadlines, monetary thresholds, approval requirements.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `type` | VARCHAR(50) | Entity type: `"requirement"`, `"deadline"`, `"threshold"`, `"approval"` |
| `name` | VARCHAR(200) | Entity value, e.g. `"12 characters"`, `"90 days"`, `"Manager approval of $10,000"` |
| `document_id` | UUID (FK) | References `documents(id)` |
| `attrs` | JSONB | Extra metadata, e.g. `{"amount": 10000, "currency": "USD", "authority": "Manager"}` |
| `created_at` | TIMESTAMP | Insertion time |

**Relationships:** Belongs to one `document`

**Note:** No embeddings or full-text search — only exact-match queries by `type` or `name`.

---

### 4. `queries` — Inbound Questions
**Purpose:** Logs every question asked by users.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `user_id` | VARCHAR(100) | Who asked the question (username from JWT) |
| `role` | VARCHAR(50) | User's access level, e.g. `"level_1"`, `"admin"` |
| `dept` | VARCHAR(100) | User's department, e.g. `"Finance"`, `"HR"` |
| `question` | TEXT | The raw question text (non-nullable) |
| `intent` | VARCHAR(50) | Classified intent: `"GENERAL"`, `"APPROVAL"`, `"CONFLICT"`, `"COMPLIANCE"`, `"PROCEDURE"` |
| `created_at` | TIMESTAMP | When the question was asked |

**Relationships:** Has many `answers`

**Indexes:** `user_id`, `created_at`

---

### 5. `answers` — LLM Responses
**Purpose:** Stores every answer generated by the LLM pipeline.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `query_id` | UUID (FK) | References `queries(id)` |
| `answer` | TEXT | The LLM-generated response text |
| `verdict` | VARCHAR(20) | `"clear"`, `"abstained"`, `"conditional"`, `"violation"` |
| `confidence` | FLOAT | 0.0–100.0 percentage score |
| `abstained` | BOOLEAN | `TRUE` if system refused to answer |
| `latency_ms` | INTEGER | Response time in milliseconds |
| `model_version` | VARCHAR(50) | Which LLM generated this, e.g. `"deepseek-r1-distill-llama-8b"` |
| `created_at` | TIMESTAMP | Insertion time |

**Relationships:** Belongs to one `query`, has many `citations` (cascade delete), has many `feedback` (cascade delete)

**Indexes:** `query_id`, `verdict`

---

### 6. `citations` — Answer-to-Source Links
**Purpose:** Tracks which chunks were cited in each answer — the audit trail for answer grounding.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `answer_id` | UUID (FK) | References `answers(id)` |
| `chunk_id` | UUID (FK) | References `chunks(id)` — which source clause was cited |
| `document_id` | UUID (FK) | References `documents(id)` — which document the chunk belongs to |
| `clause_ref` | VARCHAR(100) | The clause reference, e.g. `"4.2.1"` |
| `score` | FLOAT | Relevance score from CrossEncoder reranker (0.0–1.0) |
| `created_at` | TIMESTAMP | Insertion time |

**Relationships:** Belongs to one `answer`, references one `chunk`

**Indexes:** `answer_id`, `chunk_id`

**Note:** Three FKs are denormalized for query performance — one row gives clause, document, and score without joins.

---

### 7. `feedback` — Human Review Signal
**Purpose:** Users can rate answers (1–5 stars) and leave notes.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `answer_id` | UUID (FK) | References `answers(id)` |
| `rating` | INTEGER | 1–5 (enforced by `CHECK` constraint) |
| `note` | TEXT | Optional free-text comment |
| `reviewer` | VARCHAR(100) | Who submitted the feedback |
| `created_at` | TIMESTAMP | Insertion time |

**Relationships:** Belongs to one `answer`

**Index:** `answer_id`

---

### 8. `audit_log` — Immutable Audit Trail
**Purpose:** Append-only log of every significant action. No updates, no deletes — compliance requirement.

| Column | Type | Details |
|--------|------|---------|
| `id` | UUID (PK) | Auto-generated |
| `actor` | VARCHAR(100) | Who performed the action (username) |
| `action` | VARCHAR(50) | Action type: `"login"`, `"query"`, `"feedback"`, `"register"`, `"refresh_index"` |
| `payload` | JSONB | Action-specific data, e.g. `{"question": "Who can approve $10K?"}` |
| `ts` | TIMESTAMP | When the action occurred |

**Relationships:** None — standalone, no foreign keys

**Indexes:** `actor`, `action`, `ts`

---

## Relationship Map

```
documents
  ├── (1:N) chunks      ← clause-level text + vector embedding
  └── (1:N) entities    ← structured extractions (thresholds, deadlines)

queries
  └── (1:N) answers     ← LLM responses
        ├── (1:N) citations  ← links answer → chunk
        │     └── references chunks.id AND documents.id
        └── (1:N) feedback   ← human ratings (1-5)

audit_log                ← standalone, append-only, no FKs
```

---

## Query Flow Through Tables

```
1. User asks: "Who can approve $10K?"
   → INSERT INTO queries (user_id, question, intent)

2. Retrieve chunks from chunks table (via search.py)
   → SELECT * FROM chunks WHERE vector cosine similarity

3. LLM generates answer
   → INSERT INTO answers (query_id, answer, verdict, confidence, latency_ms)

4. Record which chunks were cited
   → INSERT INTO citations (answer_id, chunk_id, document_id, clause_ref, score)

5. Log the action
   → INSERT INTO audit_log (actor, action, payload)

6. User rates the answer
   → INSERT INTO feedback (answer_id, rating, note, reviewer)
```
